起點很單純：我有一些大型文件、錄音和影片，想先做重點彙整再交給 Claude 處理，省 token。

我自己用下來，NotebookLM 在這種多來源彙整上的結果比我把檔案一次性丟給 LLM 好。

先講清楚這句話的份量：**這是主觀比較，我沒有做過對照實驗。** 我也不知道差別來自哪裡 —— 可能是檢索方式，可能是模型或提示詞。Google 沒有公開 NotebookLM 的架構，官方說明頁通篇沒有交代底層用的是哪個模型（產品改名叫 Gemini Notebook 之後，用名字反推架構更是循環論證）。所以任何「因為它用了 X 所以比較好」的說法，包括我原本想寫在這裡的那句，都只是猜測。

我選它的**具體理由**是兩件我直接驗證過、而且最影響選型的能力（後面還有不少實測，但那些是踩坑紀錄，不是選型依據）：

- **能跨文件綜合** —— 把同一個案件的上下兩集音訊丟進去，問「上集埋的線索到下集怎麼揭曉」，三條線索都答對，而且引用分別指向正確的集數。
- **每個結論標得回原文** —— 回答帶引用，可以回頭核對。

問題是它沒有官方 API。

---

## 第一次調查：我直覺會先拿的那個已經死了

搜下去有三個主要候選：

| 專案 | Stars | 最後 push |
|---|---|---|
| teng-lin/notebooklm-py | 19,000+ | 當天 |
| PleasePrompto/notebooklm-mcp | 3,300+ | 2026-05-01 |
| roomi-fields/notebooklm-mcp | 170 | 2026-08 |

npm 上搜「notebooklm」有 108 個套件。這個生態不小。

先講清楚三者的關係，免得下面看得混亂：**star 最高的 teng-lin 那個是活的**，而且我最後用的就是它。死掉的是清單裡的第二個 —— 它 star 數雖然只有前者的六分之一，卻是 MCP 類裡最高的，也是 `npm install notebooklm-mcp` 會裝到的東西，所以是多數人（包括我）第一個會碰到的。

第二個是 npm 上 `notebooklm-mcp` 對應的專案，star 數在 MCP 類裡最高，直覺會先拿它。但最後 commit 停在 5 月 —— **早於 Google 在 2026-07-16 把 NotebookLM 改名為 Gemini Notebook 的那次事件**。

改名之後，網域從 `notebooklm.google.com` 轉到 `notebook.google.com`。那個專案的登入流程還在等舊網域，於是 `setup_auth` 永遠回報未登入。修復 PR 開了一個月沒 merge。

**它用的是 Patchright 瀏覽器自動化。** 同一次改名，走逆向 RPC 的 `notebooklm-py` 毫髮無傷。

這是我後面所有判斷的第一塊拼圖。

---

## 繞路一：官方免費方案，方向是相反的

在決定用非官方方案之前，我先確認官方路走不走得通。

Google 確實有官方的 managed RAG —— Gemini API 的 **File Search**，GA 狀態，免費 API key 就能用，索引和查詢的 embedding 都免費，而且支援引用溯源。

看起來是正解。直到我去讀條款。

`ai.google.dev/gemini-api/terms` 原文：

> When you use **Unpaid Services**... Google uses the content you submit **to provide, improve, and develop Google products and services and machine learning technologies**...
>
> To help with quality and improve our products, **human reviewers may read, annotate, and process your API input and output.**
>
> **Do not submit sensitive, confidential, or personal information** to the Unpaid Services.

而 NotebookLM 消費者版的官方說明頁（`support.google.com/notebooklm/answer/16164461`）：

> Your data is protected, and is **not used to train Gemini Notebook unless you provide feedback.**

**方向相反。** 官方免費 API 更穩定，但條款允許 Google 把你提交的內容用於「提供、改進及開發產品與 machine learning technologies」，人工可閱讀，而且明文叫你不要提交機密內容。NotebookLM 消費者版則明文寫「不用於訓練，除非你提供意見回饋」。

要注意這兩者的差別是**用途**不是**去向** —— 兩條路資料都會進 Google。我原本寫「非官方路線資料不外流」是講過頭了，官方明文保證的是不拿去訓練，不是不接觸。

我要處理的是自己的非公開文件，所以隱私權重高於穩定性。

順帶一提，免費 tier 的 File Search 語料庫上限只有 1 GB，而且**明文不支援音訊影片索引**。就算條款沒問題，我的用途也裝不下。

## 繞路二：那我自己做瀏覽器自動化呢？

既然逆向 API 會壞，直覺會想：那我開個真的 Chrome，跑固定腳本，甚至存一張 golden 截圖比對版面有沒有跑掉，不就好了？

我認真評估過。結論是**更糟**，而且理由不只一個。

**第一，ToS 上大概不豁免。** Google 條款的字眼是 "using **automated means** to access content"。字面可查證，但「所以換傳輸方式不會豁免」是**我的解讀**，不是條款直接寫出來的結論 —— 我不是律師，這也不是法律意見。依這個解讀，用 Playwright 驅動真 Chrome 一樣落在 automated means 裡面。

**第二，UI 可能比內部 API 更容易壞。** 這點反直覺。以下是我的推論，**不是量測數據** —— 我沒有統計過兩者的實際改版頻率：

| | 內部 RPC | 前端 UI |
|---|---|---|
| 我實際觀察到的 | 固定的 rpc id，跨多次呼叫沒變 | 生成式 class name |
| 我推測的依賴面 | 可能有其他 client 依賴，改動要顧相容 | 主要服務畫面本身 |
| 我推測的改動成本 | 較高 | 較低 |

這個推論唯一的硬證據是上面那個案例：3,300 star 的專案死於改名事件，而同一次改名沒有影響走 RPC 的那個。一個案例不足以證明通則，但足以讓我不敢把賭注押在 UI 上。

**第三，golden image 比對大概解決不了問題。** 這段我沒有實際做過，是評估階段的判斷：它能告訴你「畫面變了」，但不會告訴你怎麼修；A/B test、字型渲染、串流中的回答文字都會讓 diff 亮紅燈；而聊天回應是逐字串流出現的，截圖時機不同結果就不同。你會多養一套本身也會腐化的維護工作。

**第四，用 F12 讀內容會繞回原點。** 腳本能用的是 CDP（Chrome DevTools Protocol）。如果用它去攔網路回應，攔到的就是同一批 `batchexecute` 回應 —— 你還是得解那個未公開的格式，外加養一個瀏覽器。嚴格劣於直接打。

## 那實際上是怎麼運作的？

底層打的是這個：

```text
POST https://notebook.google.com/_/LabsTailwindUi/data/batchexecute
       ?rpcids=<6碼方法代號>&f.sid=<session>&rt=c

body:   f.req=<URL-encoded 三層巢狀陣列>&at=<CSRF token>
cookie: 你的 Google session
```

`batchexecute` 這種路徑形式在 Google 的網頁產品上很常見，不過我沒有逐一查證哪些產品在用，這裡只講我實際看到的 NotebookLM。路徑裡的 `LabsTailwindUi` 看起來是前端模組的內部名稱，至於 Tailwind 是不是專案代號，那是我從路徑名猜的。

那些六碼字串看起來是未公開的方法代號（是不是「混淆」產生的我不確定）。**上游是怎麼取得對應關係的，我不知道** —— 我沒問過作者，也沒看過他的說明。能直接讀到的事實是：套件裡有一份自己刻的編碼解碼器，和一張硬編的方法代號表。

**所以就我觀察到的來說，這不是破解，是把你瀏覽器本來就在發的請求改用腳本發。** 同一個帳號、同一份資料、同一個端點，認證方式一模一樣，也沒有取得任何你原本無權存取的東西。

至於這算不算「繞過防護機制」—— 那是 Google 的安全分類，我從外部無從驗證，所以我不會替他們下這個結論。

差別只在發請求的是腳本而不是瀏覽器。

## 定案：用它的 CLI，不用它的 MCP

`notebooklm-py` 一個套件提供三個進入點：

```text
notebooklm          CLI          ┐
notebooklm-mcp      MCP server   ├─ 共用同一個 NotebookLMClient
notebooklm(Python library)      ┘
```

生態裡幾乎所有專案都在做 MCP server —— 把 NotebookLM 接進你的 AI 助手。我一開始也裝了。

**但我要的是一個排程跑的 bot，不是對話工具。** 在我採用的接法裡，是模型去選擇並呼叫 MCP tool，所以每次上傳、每次提問都會讓模型參與，也就都在燒 token。

這是**我的整合方式**造成的成本，不是 MCP 協定規定非如此不可 —— 協定本身沒有禁止別的觸發方式。但對我的用途來說結果一樣：模型待在迴圈裡，而我的整個目的就是省 token。

我後來把 MCP 註冊移除了，理由是實測出來的：

- **對話延續不需要 MCP。** 我原本以為只有 MCP 能做互動追問。實測兩個完全獨立的行程呼叫 `notebooklm ask`，回傳同一個 `conversation_id`，`turn_number` 從 11 遞增到 12，而且第二次問「你剛剛列的第二種模式有什麼風險」被正確解析。這證明的是**狀態不依賴單一 client 行程**；至於狀態實際存在哪裡，我推測是服務端維護，但沒有直接驗證。
- **MCP 沒給任何 CLI 做不到的事**，卻要 33 個 tool schema 常駐在 context。
- **MCP server 啟動就會呼叫 `RotateCookies`**（這是實測看到的）。我診斷它連線問題時反覆啟動又中途 kill，CLI 的憑證跟著壞掉 —— 兩者可能在搶同一份憑證狀態，但這是我從相關性推的解釋，沒有單獨做實驗證明。

同樣的判斷也套用在資料來源上。我另一個專案有 MCP server 供查詢 AI 新聞，但它的 tool 全是普通 Python 函式加 `@mcp.tool()` 裝飾器 —— **直接 `import` 呼叫，輸出跟走 MCP 協定逐字相同，但零 token。**

所以最終的組合是：

```text
上游的逆向 CLI(別人做的,MIT)
        ↓
我的確定性包裝層(PowerShell,零 LLM)
        ↓
agent 只在兩個點介入:決定問什麼 / 壞掉時修
```

## 幾個只有踩下去才會知道的坑

### 上傳成功不等於可用

`source add` 回傳成功時，音訊還在轉錄。40 分鐘的節目上傳只要幾秒，之後會停在 `preparing` 一分鐘以上。

排程如果 ingest 完立刻 digest，會問到空的來源。後來加了 `-Wait` 輪詢到全部 ready 才回傳。

### 而且「全部 ready」我第一次也寫錯了

我的判定寫 `status -eq 'failed'`，但上游實際用的字串是 `'error'`。結果 notebook 裡明明有一筆壞掉的來源，它還是印「All sources ready」然後回傳成功 —— **正是這個功能該防止的靜默成功。**

### 憑證的壽命很奇怪

解開憑證檔逐欄看到期時間：

```text
__Secure-1PSIDRTS   剩 0.2 小時(約 12 分鐘)  ← 輪替 token
__Secure-1PSIDTS    剩 8760 小時
SAPISID / SID       剩 9555 小時
```

我推測那個 12 分鐘的輪替 token 一旦錯過續期，可能會讓整組憑證脫鉤 —— 這是解釋，不是我驗證過的機制。

我在一個工作階段內把憑證弄失效三次，三次都發生在並行呼叫期間（PowerShell 與 Bash 交錯、加上反覆啟動 MCP 探測）。**樣本只有三次，我沒有做過對照實驗**，「輪替會使前一個 token 失效」是我從這個相關性推出來的解釋，不是驗證過的機制。但它足以讓我在排程設計上避開並行。

好消息是：`notebooklm login` 在瀏覽器 profile 的 Google session 還有效時**是完全非互動的**，直接重新匯出 cookie。所以排程可以在開頭做健檢、失效時自己救回來，不需要人。

### 我自己弄壞的那次

我想「加固一下憑證檔權限」，跑了：

```powershell
icacls ~/.notebooklm /inheritance:r /grant:r "User:(OI)(CI)F" /T
```

`(OI)(CI)` 是**繼承旗標**，只對目錄有意義。用 `/T` 套到葉節點檔案時產生的是「只供繼承」的 ACE，對檔案本身不授予任何權限；`/inheritance:r` 又把繼承來的移掉 —— 檔案變成零授權，連擁有者都讀不到。

然後因為讀寫都被擋，cookie 輪替寫不回去，憑證跟著過期。

**而我當時只驗了目錄的 ACL 就宣告完成，沒驗檔案。** 這個加固後來整個回退了：它在單人機器上本來就擋不住以自己身分執行的程序，價值低，而破壞性已經證實。真正有效的防線是版本凍結 —— 把套件鎖在特定版本，不讓它每次啟動從 PyPI 抓未審查的新程式碼。

### 一個關於「省 token」的反諷

NotebookLM 預設回答很長。四個問題產出 50,791 bytes，而我的目的是省 token。

加了一個附帶簡潔指令的 `-Brief` 模式後降到 2,379 bytes，21 倍。但代價是引用溯源會不見 —— 我一度以為是必然的，後來在另一個 notebook 上測又正常回傳引用。所以最後文件寫的是「不保證存在」，而不是我原本斷言的「必然失去」。

**推翻自己前一個結論，比堅持它有用。**

## 誠實的結論

程式碼本身沒什麼特別。逆向工程不是我做的，CLI 不是我做的，包裝腳本任何人半天能寫，而且它是 Windows PowerShell 專用 —— 對多數人是負分。

有價值的是**判斷的軌跡**：

- 為什麼我最先想拿的那個方案不能用（它在改名事件後失效，而它依賴的正是瀏覽器 UI）
- 為什麼官方免費方案不符合我的用途（條款對資料用途的方向與我的需求相反）
- 為什麼我不自己做瀏覽器自動化（我推測它更容易受 UI 改版影響，但手上只有一個案例）
- 為什麼我用 CLI 不用 MCP（在我的接法裡 MCP 會讓模型參與流程，而我沒測到它提供 CLI 沒有的必要能力）

每一條後面的括號都是**我的判斷**，不是通則。換一個人、換一種接法，結論可能不同。

以及那幾條把東西弄壞才會知道的事實。

**選型的價值不在選了什麼，在於排除了什麼、以及排除的理由站不站得住。**
