Claude Code has Remote Control (`/rc`): type `/rc` in a terminal session and you can continue that same session from the Claude app on your phone. Checking progress, answering a question, telling it to keep going — all from wherever you are.

There's one catch: **someone has to type `/rc` at the computer.**

Sessions that are already running are fine. The problem is when I'm out and want a **new** session for a different task. A new session opens in a terminal on my desktop, nobody is there to type `/rc`, and my phone can't reach it.

## The fix: start new sessions already in /rc

The `claude` CLI has a `--remote-control` flag that does the same thing as typing `/rc` after launch. The only missing piece was "open a new window and run that in a given directory." So I wrote `new-rc-session.ps1`. The core is a few lines:

```powershell
param(
    [string]$Path = 'C:\GitSource',
    [string]$Name = ''
)

# Always name the session so it can be closed by name later
if (-not $Name) { $Name = 'rc-' + (Get-Date -Format 'yyyyMMdd-HHmmss') }

# Build the command as one string: PS 5.1 silently drops empty native args
$cmd = "claude --remote-control '" + ($Name -replace "'", "''") + "'"

Start-Process powershell -WorkingDirectory $Path -ArgumentList '-NoExit', '-Command', $cmd
```

In practice the flow looks like this:

1. On my phone, open a session that is **already in /rc mode**
2. Tell it "open a new session in directory X"
3. It runs the script on my computer → a new window pops up with Claude Code already in Remote Control mode
4. Once it registers (it takes a few seconds), the new session shows up in the phone app's list, and I tap into it

In other words, **as long as one /rc session stays open on the computer, it's my doorway for starting new sessions from the phone.**

## A gotcha: PowerShell 5.1 silently eats empty arguments

The intuitive approach is to pass each argument separately to the external program. But when Windows PowerShell 5.1 calls a native exe, it **silently drops** empty-string arguments — no error, no warning — and `claude` ends up receiving different arguments than you think.

The fix is to build the whole command as **a single string** before handing it to `-Command`, escaping any single quotes in the name. Failures that produce no error message, just a wrong result, are the hardest to track down, so I left a comment in the script for my future self.

## Why every session gets a name

If you don't pass a name, the script names the session something like `rc-20261021-143005`. The design principle: **if you can open it, you need to be able to close it.**

After opening a few sessions from the phone, several `claude.exe` processes pile up on the computer. In my testing, an RC session started without a name shows an empty name column in `close-session.ps1`'s list — you can only tell it apart by PID and start time, which makes it easy to close the wrong one.

So it comes with a companion, `close-session.ps1`:

- `-List` shows every local Claude Code session (PID, name, mode, status, start time)
- `-Name` or `-Id` picks the one to close
- Safety rules are hard-coded in the script: **never close the session running the script**, the target must be `claude.exe`, and a name must match **exactly one** session — otherwise nothing is closed

When an AI is the one killing processes, I'd rather it refuse a few extra times than guess wrong once.

## Wrap-up

It's a small thing: one CLI flag, one new window, one auto-generated name. But it removes the "you have to be at the computer for every new session" constraint — as long as the computer is on and one /rc session is open, I can start a new line of work from anywhere.

A few takeaways:

- **Look for an existing flag first.** No need to simulate keystrokes to type `/rc`; the CLI already supports `--remote-control`.
- **If you can open it, you must be able to close it.** The auto-naming exists for closing, not for looks.
- **For destructive operations an AI will run, put the safety checks in the script**, not in a prompt you hope it follows.

## Postscript: I tried the official server mode, and went back to my script

There's a premise I didn't spell out above: **the first /rc session still has to be opened at the computer.** I wasn't sure whether there was a more efficient way, so after publishing I went back to the official docs, found server mode, and actually tried it.

The [Remote Control documentation](https://code.claude.com/docs/en/remote-control) describes server mode: run `claude remote-control` on the computer and it stays up waiting for connections, with up to 32 concurrent sessions by default, and `--spawn worktree` to give each session its own git worktree.

**What I tested** (Claude Code 2.1.306, server started in `C:\GitSource`):

- On startup the server pre-creates one session. The phone app could connect to it, and the computer responded to what I typed. But that's no different from the plain /rc approach.
- What I actually wanted to test was **starting a new session from the phone**. The app required the **Claude desktop app** to be running on the computer, and showed a folder picker limited to pre-approved working directories.
- The server itself also has to be started at the computer, so the "first step happens at the desk" problem doesn't go away.

Checking back against the docs: the [mobile page](https://code.claude.com/docs/en/mobile) lists Remote Control (connecting to a Claude Code session running on your computer) and Dispatch (connecting to the desktop app on your computer) as two separate mechanisms, and for a local session says: "Start the session on your computer with `claude remote-control`, or run `/remote-control` in a session that's already open." My inference is that starting a new session from the phone actually went through the desktop app path, not server mode itself; the docs don't say which one I hit. That said, the remote-control page's description of `--chrome` mentions "any session you start yourself from claude.ai/code or the Claude app," which suggests server mode may support starting sessions from the app too — I just didn't reach that path in my test. As for server mode's on-demand sessions, the docs say they use the server's working directory (or worktrees under it), and say nothing about choosing a different directory from the phone.

| | My script | Official server mode |
|---|---|---|
| First step at the computer | Yes (open the first /rc session) | Yes (start the server) |
| Working directory of new sessions | Any directory, chosen each time | The server's directory (or worktrees under it) |
| Starting a new session from the phone | Ask an existing /rc session to run the script | In my test, the app required the desktop app and only allowed pre-approved folders |
| Multiple sessions | Each is its own window and process | One server manages many sessions |

**Conclusion: I'm sticking with my script.** My judgment: server mode fits better when running many sessions inside one fixed project; what I need is to switch working directories at will, and for me the script does that more directly. Of the three takeaways above, "look for an existing flag first" still held: I looked, I tried it, and only after confirming the built-in option didn't fit did I keep my own.
