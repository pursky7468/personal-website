# Blog Content Rules

## Agents

Blog 工作流遵循 `~/.claude/rules/frontend-publish.md` 的 4 步驟標準流程。

- Publisher: `subagent_type: web-content-publisher`
- Reviewer: `subagent_type: web-content-reviewer`
- Config: `blog-publish.config.json`（專案根目錄）

不要在主對話中直接寫 blog 內容，改用 `Agent` tool 並指定對應的 `subagent_type`。

## 格式規範

- 副檔名一律 `.mdx`（不使用 `.md`）
- 若來源是 `.md`：建立 `.mdx` 後刪除原檔

### Frontmatter schema

```yaml
---
title: ""
date: YYYY-MM-DD
tags: []
summary: ""   # 一句話，≤160 chars
draft: false
---
```

## Reviewer 必查項目

除格式外，reviewer **必須**檢查以下內容，任何一項 FAIL 就整體 FAIL：

- **素材可溯性**：所有第一人稱經驗描述（「我發現…」「有一次…」「實踐後…」）必須能對應到 publisher 收到的素材。無法對應的一律視為虛構，標為 FAIL。
- **無捏造事實**：不可有未發生的使用經驗、未存在的測試結果、未實際觀察到的數據。
- **機密邊界**：見下節。素材來自公司／客戶內部資料時，此項為**最高優先**，且 publisher 的自陳一律不採信，reviewer 必須自行掃描全文。

## 證據等級標示（硬規則，FAIL 條件）

「無捏造事實」擋得住編造，擋不住**把推論寫成事實**。後者更難察覺，因為每個字都是真心話。

**每一項有實質內容的宣稱，都必須能歸到以下四級之一：**

| 等級 | 定義 | 是否必須顯式標明 |
|---|---|---|
| **實測** | 本次工作中親自跑過，有實際輸出佐證 | 否（但要寫出怎麼測的） |
| **查證** | 引用外部一手來源（官方文件／條款／API 回應） | 否（但要附連結或原文） |
| **主觀** | 個人使用印象、偏好，未做對照實驗 | **是** |
| **推論** | 從已知事實推導，但沒有直接驗證 | **是** |

**規則：**

1. **主觀與推論必須在句子附近顯式標明**，不可用敘述句的語氣混入。
   寫「我沒有做過對照實驗」「這是我的推論，不是量測數據」「我不知道原因」。
2. **機制解釋是最高風險區。** 「A 比 B 好，因為 A 用了 X」這種句型要拆開看：
   「比較好」通常是**主觀**，「因為 X」幾乎一定是**推論**。兩個都要標。
3. **不知道就寫不知道。** 「上游怎麼做到的我不知道」比一個聽起來合理的猜測有價值。
4. **不要用產品名反推技術架構。** 產品叫什麼不構成它底層用什麼的證據。
5. 推論本身**不必刪除** —— 讀者要的正是判斷過程。要刪的是**冒充事實的語氣**。

**驗證機制:**

```powershell
npm run verify:claims -- <slug>        # 單篇（publisher 在 commit 前必跑）
npm run verify:claims:all              # 全站重掃（規則異動後跑）
node scripts/verify-claims.js --file draft.md   # 草稿階段就能跑
```

已加入 `blog-publish.config.json` 的 `verifyCommands` 第一順位——它讀本機檔案，
不必等部署，內容問題也比版面問題嚴重。

**腳本的已知限制（別把 PASS 當作背書）:**

- 它**認關鍵字，不懂語意**。「語氣像事實但其實在猜」的句子抓不到，這正是它需要
  搭配人工判讀的原因。
- **英文覆蓋率低於中文**。中文有 5 組句型規則，英文只有 4 組且較保守。
  英文文章 PASS 的可信度低於中文，reviewer 對 `.en` 要更用力看。
- 它**只檢查有沒有標**，不檢查標得對不對。把推論標成「實測」它一樣放行。
- `{/* claims-ok: 理由 */}` 是逃生門，用它就等於宣告「我確認過這是實測或查證」。
  理由要寫清楚，reviewer 會查。

**Reviewer 執行方式（兩層，缺一不可）：**

1. **機械掃描**——跑 `node scripts/verify-claims.js <slug>`，它會標出高風險句型
2. **人工判讀**——逐項確認：這句是哪一級？如果是主觀或推論，附近有沒有標？
   腳本只認關鍵字，認不出「語氣像事實但其實在猜」的句子

發現問題時標明**行號**與該句應屬的等級；**不要自行改寫論點**，交回給作者決定要標註還是刪除。

## 機密邊界（素材來自非公開資料時必查）

判準只有一條：**讀者不應該能認出這是哪家公司的哪個系統**。「有沒有貼程式碼」不是分界。

**禁止出現**：公司名、產品名、客戶名、專案代號、真實類別／型別／欄位名、真實檔案路徑、
內部組件名、內網或 GitLab 網址、色碼、產品序號、IP。

**允許出現**：

- 通用公開 API 名（`RenderTargetBitmap`、`AppDomain.AssemblyResolve`、`ScrollViewer`…）
- 中性代稱（「主程式」「設定頁」「宿主視窗」「某個相依組件」）
- 去識別化後的實測數字與方法論

**執行方式**（兩層，缺一不可）：

1. **機械掃描**——對全文 grep 專案相關的專有名詞清單，回報命中數
2. **人工判讀**——grep 抓不到「換句話說但仍可辨識」。要特別檢查：私有欄位名／資源 key 前綴
   等殘留識別碼，以及「多個品類資訊疊加後是否足以指認」

發現可疑項時標明**行號**並說明為什麼可辨識；**不要自行刪改**，交回給人決定——
有些描述刪掉會損失文章核心論證，該不該留是作者的判斷，不是 reviewer 的。

### 對 publisher 的連帶要求

素材為非公開來源時，**publisher 不得直接讀取原始機密資料夾**。
必須由主對話先產出一份**去識別化的中介素材檔**，publisher 只讀那一份。

## 版面驗證重點

- 表格是否渲染為 HTML table（有框線），而非原始 `|` 字元
- Code block 是否有語法高亮
- 有無亂碼（`???`、方塊字、`â€` 等）
- 標題層級是否正確，排版是否易讀

### 常見問題

| 症狀 | 原因 | 修法 |
|---|---|---|
| 表格顯示原始 `\|` | `remark-gfm` 未啟用 | 確認 `contentlayer.config.ts` 有 `remarkPlugins: [remarkGfm]` |
| Code block 無高亮 | `rehype-pretty-code` 問題 | 確認 `rehypePlugins` 有 `rehypePrettyCode` |
| 中文變 `???` | PowerShell pipe encoding | 改用 `cmd /c '... < utf8file'`，不用 pipe |
